1. Bức Tranh Tổng Thể Kiến Trúc Dự Án Architecture Overview

Chương trình mô phỏng kiến trúc chuẩn của FTP (RFC 959) kết hợp với tầng truyền tải tin cậy tự phát triển trên nền UDP:

Hai Kênh Truyền Độc Lập:
  • Kênh Điều Khiển (Control Channel - TCP Port 8080): Dùng TCP để trao đổi các lệnh text giữa Client và Server (USER, PASS, STOR, RETR, PORT, PASV, ABOR,...). Cổng 8080 là cổng cố định (Well-known Port) duy nhất mà Client kết nối ban đầu. Kênh này duy trì xuyên suốt phiên làm việc.
  • Kênh Dữ Liệu (Data Channel - UDP RDT): Dùng UDP để truyền/nhận nội dung file thật hoặc danh sách thư mục. Hệ thống tự cài đặt giao thức tin cậy RDT (Reliable Data Transfer) với thuật toán Go-Back-N (Sliding Window) kết hợp Congestion Control (AIMD - Additive Increase/Multiplicative Decrease), Internet Checksum 16-bit và Cumulative ACK.
Mô hình Xử lý Đa Luồng (Thread-per-connection): Mỗi Client kết nối vào Server sẽ được cấp 1 Thread chính xử lý kết nối. Khi có lệnh truyền dữ liệu (STOR/RETR/...), Server tiếp tục tách thêm 1 Thread phụ (transferThread) để truyền dữ liệu qua UDP. Nhờ vậy, Kênh Điều Khiển chính hoàn toàn rảnh rỗi để nhận lệnh mới bất kỳ lúc nào (kể cả lệnh ABOR để hủy transfer đang chạy).

Cấu trúc dự án: SERVER/ chứa mã nguồn Server; CLIENT/ chứa mã nguồn Client. Các file RdtPacket.h, RdtPacket.cpp, DataChannel.h, DataChannel.cpp ở hai bên giống hệt nhau (byte-by-byte) do tính đối xứng của giao thức RDT.

2. Luồng Hoạt Động End-to-End Chi Tiết System Workflow
2.1 Bắt tay kết nối & Khởi tạo phiên
  • 1. Server khởi động Winsock, tạo thư mục gốc server_root/, lắng nghe TCP cổng 8080.
  • 2. Client kết nối tới Server qua IP và Port 8080.
  • 3. Server accept() kết nối -> Tạo luồng riêng (Detached Thread) chạy ControlChannel::handleClient(), phản hồi 220 Service ready.
  • 4. Server khởi tạo đối tượng Session (lưu trạng thái Client) và CommandHandler.
2.2 Vòng lặp nhận và thực thi lệnh
  • Client: Luồng chính đọc bàn phím (ftp> ), luồng nền riêng (receiverThread) liên tục recv() câu trả lời từ Server. Tách 2 luồng giúp bàn phím không bị khóa khi đang truyền file, cho phép gõ ABOR ngắt lệnh.
  • Server: Nhận dòng lệnh TCP -> Gọi parseCmd() tách lệnh và tham số -> Gọi CommandHandler::handle() thực thi qua enum FtpCommand.
2.3 Luồng truyền file (STOR / RETR / STOU / APPE)
  • 1. Server nhận lệnh -> Tạo DataChannel (UDP), bind cổng 0 để OS cấp cổng ngẫu nhiên.
  • 2. Server lấy cổng thật bằng getBoundPort() và đính kèm vào phản hồi 150 qua chuỗi " PORT=" (trừ chế độ PASV).
  • 3. Server tạo transferThread chạy ngầm truyền dữ liệu UDP -> Luồng chính tiếp tục lắng nghe TCP.
  • 4. Client nhận phản hồi 150 -> Đọc cổng ngẫu nhiên parseEmbeddedPort() -> Kích hoạt truyền dữ liệu RDT qua UDP.
  • 5. Hoàn tất -> Server gửi phản hồi 226 Transfer complete (hoặc 426 nếu bị ngắt).
3. Cơ Chế RDT — Go-Back-N & Congestion Control AIMD Transport Layer Core
Cấu Trúc Gói Tin RDT Packet

Header gói tin RDT gồm 9 Bytes định dạng Big-Endian:

[seqNum: 4B] [flags: 1B] [checksum: 2B] [payloadLength: 2B] [payload: N Bytes]
  • seqNum: Số thứ tự gói tin tăng dần (0, 1, 2...). Trong gói ACK là Cumulative ACK (seq lớn nhất nhận liên tục). Trong gói FIN là tổng số khối DATA đã gửi.
  • flags: Cờ phân loại: FLAG_DATA (0x01), FLAG_ACK (0x02), FLAG_FIN (0x04).
  • checksum: Internet Checksum 16-bit (1's complement sum).
  • payloadLength: Kích thước byte thực tế phần dữ liệu.
Thuật Toán Go-Back-N & AIMD Phía Gửi (rdtSend)
Cơ chế cửa sổ trượt (Sliding Window):
  • Toàn bộ file được chia nhỏ thành các khối tối đa 1024 Bytes (RDT_MAX_PAYLOAD) và đóng gói sẵn.
  • Sử dụng 3 biến: base (biên trái cửa sổ), nextSeq (biên phải cửa sổ), window (kích thước cửa sổ hiện tại).
  • Timer duy nhất: Chỉ canh đo timeout cho gói base (gói cũ nhất chưa ACK) theo mốc thời gian 500ms (RDT_TIMEOUT_MS).
  • Poll Socket: Thực hiện recvfrom() kiểm tra ACK mỗi 50ms (RDT_POLL_MS).
  • AIMD Additive Increase: Mỗi khi nhận ACK hợp lệ trượt base tiến lên, tăng cửa sổ: window = min(window + 1, RDT_MAX_WINDOW) (tối đa 32).
  • AIMD Multiplicative Decrease: Khi quá hạn timeout (500ms), giảm cửa sổ: window = max(window / 2, RDT_MIN_WINDOW) (tối thiểu 1) và gửi lại toàn bộ các gói trong cửa sổ từ base đến nextSeq - 1.
Thuật Toán Go-Back-N Phía Nhận (rdtReceive)
Quy tắc tiếp nhận gói tin:
  • Đúng thứ tự (seqNum == expectedSeq): Nhận dữ liệu vào bộ nhớ, tăng expectedSeq++, gửi Cumulative ACK.
  • Trùng lặp (seqNum < expectedSeq): Bỏ qua dữ liệu, gửi lại Cumulative ACK cũ.
  • Bất ngờ / Lệch thứ tự (seqNum > expectedSeq): LOẠI BỎ hoàn toàn gói tin, không đệm (Buffer). Gửi Cumulative ACK cho gói hợp lệ cuối cùng.
  • Gói lỗi (Checksum Failure): Bỏ qua âm thầm, không phản hồi ACK để phía gửi tự Timeout.
4. Cơ Chế Thương Lượng Cổng UDP Ngẫu Nhiên (Ephemeral Port) Networking Improvement

Khắc phục hoàn toàn xung đột cổng cố định khi mở nhiều Client trên cùng một máy tính:

  • Nguyên lý: Thay vì cố định cổng 8081/8082, khi tạo Socket UDP, ứng dụng gọi bind() với port = 0. Hệ điều hành tự động cấp phát 1 cổng ngẫu nhiên chưa sử dụng.
  • Đọc cổng thực tế: Gọi getsockname() qua hàm getBoundPort() để lấy số cổng OS vừa cấp.
  • Thông báo qua TCP: Server chèn " PORT=" vào phản hồi 150. Client đọc chuỗi này để biết địa chỉ UDP Server đang chờ kết nối.
  • Tự động thương lượng ACTIVE (autoNegotiateActivePort): Khi người dùng gõ RETR ở phía Client mà chưa thiết lập PORT/PASV, Client tự động tạo Socket UDP ngẫu nhiên, lấy IP/Port và tự gửi ngầm lệnh PORT sang Server trước khi gửi lệnh RETR.
5. Kỹ Thuật Lõi & Bài Học Kinh Nghiệm Best Practices
Bảo Vệ Bộ Nhớ & Khóa Tranh Chấp

Sử dụng std::lock_guard<std::mutex> cho g_coutMutex chống đè màn hình Console. Sử dụng std::atomic<SOCKET> bảo vệ đóng socket an toàn giữa nhiều luồng.

Sửa Lỗi Double Free Crash

Quản lý vòng đời con trỏ DataChannel bằng std::shared_ptr. Hàm setActiveDataChannel() chỉ lưu địa chỉ quan sát, tuyệt đối không gọi delete thủ công.

Chống Tấn Công Path Traversal

Sử dụng hàm resolvePath() chuẩn hóa bằng lexically_normal() và ánh xạ tuyệt đối với fs::weakly_canonical() dưới thư mục gốc SERVER_ROOT.

Bảo Tồn Thứ Tự Lệnh TCP

Gọi joinPreviousTransfer() đảm bảo luồng truyền file trước đó đã kết thúc hoàn toàn trước khi khởi tạo luồng truyền file mới.

7. Mô Đun Gói Tin RDT (RdtPacket.h / RdtPacket.cpp) Dùng Chung
uint16_t computeChecksum(const char* data, int length)
Tính checksum kiểu Internet (1's complement sum) cho mảng byte.
Chi tiết thuật toán:
  • 1. Duyệt mảng byte theo từng cặp 2 bytes, ghép thành 1 số 16-bit Big-Endian (data[i] << 8) | data[i+1] và cộng dồn vào biến sum 32-bit.
  • 2. Nếu tổng số bytes là lẻ, byte cuối cùng được dồn lên 8 bit cao data[i] << 8 (pad thêm byte 0x00 vào sau).
  • 3. Fold carry: Vòng lặp cộng phần tràn 16-bit cao vào 16-bit thấp sum = (sum & 0xFFFF) + (sum >> 16) cho đến khi không còn tràn.
  • 4. Thực hiện đảo bit ~(uint16_t)sum và trả về kết quả 16-bit.
bool verifyChecksum(const char* data, int length)
Xác minh tính toàn vẹn của gói tin đã serialize nhận được.

Tính tổng 1's complement trên TOÀN BỘ mảng byte. Nếu gói tin không lỗi, tổng thu được phải bằng 0xFFFF (đảo bit bằng 0). Trả về true nếu hợp lệ.

vector<char> serializePacket(const RdtPacket& pkt)
Chuyển đổi struct RdtPacket thành mảng byte chuẩn mạng (Big-Endian) để gửi qua Socket UDP.
bool deserializePacket(const char* data, int length, RdtPacket& outPkt)
Giải mã mảng byte nhận từ UDP Socket thành struct RdtPacket với đầy đủ các bước kiểm tra header và checksum.

Đặc biệt, ở phía Client, hàm có cơ chế đo đếm thời gian thực và in ra tiến độ Upload (phần trăm hoàn thành, số lượng gói tin) định kỳ mỗi 1 giây.

Các hàm bọc cấp cao phục vụ đọc/ghi file trực tiếp ra đĩa cứng và hỗ trợ NAT Traversal (Probe) cho chế độ PASSIVE mode.

12. Kênh Điều Khiển Phía Server (ControlChannel.h / ControlChannel.cpp) Server
ControlChannel::run() & handleClient()
Vòng lặp accept() liên tục nhận Client TCP mới. Mỗi Client chạy trong một luồng std::thread độc lập ở chế độ detach(). Đọc câu lệnh, gọi CommandHandler::handle() và gửi phản hồi.
Tích Hợp Active Session Table (SessionRegistry)
handleClient() đồng bộ trạng thái từng Client vào bảng session toàn cục xuyên suốt vòng đời kết nối:
  • SessionRegistry::add(clientSocket, clientIp): đăng ký session ngay lúc accept() thành công, in bảng ra console ngay lập tức.
  • SessionRegistry::update(...): gọi sau mỗi lệnh xử lý xong, cập nhật username, trạng thái đăng nhập, thư mục hiện tại và lệnh vừa chạy.
  • SessionRegistry::remove(...): gỡ session khỏi bảng khi Client ngắt kết nối (QUIT hoặc mất kết nối đột ngột), in lại bảng để phản ánh trạng thái mới nhất.
ControlChannel::adminConsoleLoop()
Một luồng nền riêng (detach() song song với vòng lặp accept()) đọc lệnh admin từ bàn phím Server. Gõ sessions (hoặc who) bất cứ lúc nào để in ngay bảng session đang hoạt động ra console — phục vụ trực tiếp cho việc quan sát log và test đa Client đồng thời lúc demo.

class SessionRegistry (static, toàn cục)
Bảng static map<SOCKET, ClientRecord> table, bảo vệ bởi static mutex mtx riêng — vì nhiều Client (nhiều thread) có thể thêm/sửa/xóa đồng thời.
  • add(sock, ip): tạo bản ghi mới khi Client vừa accept().
  • update(sock, userName, loggedIn, currentDir, lastCommand): cập nhật sau mỗi lệnh; tự bỏ qua an toàn nếu socket đã bị remove() (tránh race hiếm).
  • remove(sock): xóa bản ghi khi Client ngắt kết nối.
  • count(): trả về số session đang hoạt động — hữu ích khi test nhiều Client đồng thời.
  • printTable(): khóa cả mtx lẫn g_coutMutex, in ra bảng dạng cột (IP, User, LoggedIn, CurrentDir, LastCmd) kèm tổng số session.
Bảng được in tự động mỗi khi có Client connect/disconnect, và có thể xem lại bất cứ lúc nào bằng lệnh admin sessions gõ trực tiếp trên console Server (xem ControlChannel::adminConsoleLoop() ở mục 12).

15. Kênh Điều Khiển Phía Client (ControlChannel.h / ControlChannel.cpp) Client
Kiến Trúc Đa Luồng Phía Client (3 Luồng)
  • Luồng chính (Keyboard Loop): Đọc câu lệnh nhập từ bàn phím (cin). Tách lệnh/đối số theo dấu cách đầu tiên. Tự động gọi autoNegotiateActivePort() nếu gõ RETR mà chưa PORT/PASV. Luồng này hoạt động song song để người dùng gõ lệnh mới bất cứ lúc nào.
  • Luồng TCP Nhận (receiverLoop): Nhận phản hồi và mã trạng thái liên tục từ Server. Khi nhận phản hồi 150 (báo hiệu mở kênh truyền dữ liệu), luồng này sẽ kích hoạt doDataTransfer() chạy trong một luồng phụ tách biệt độc lập (Detached Thread).
  • Luồng Truyền Tải Dữ Liệu Phụ (doDataTransfer Thread): Luồng được tạo dưới dạng bất đồng bộ (std::thread(...).detach()) đảm nhận nhiệm vụ truyền tải file qua UDP RDT. Nhờ tách luồng này, luồng TCP Nhận (receiverLoop) không bị block, cho phép Client tiếp tục nhận và xử lý các phản hồi tiếp theo từ Server (ví dụ: phản hồi của lệnh ABOR hoặc các lệnh thông tin khác).
Đồng Bộ Prompt "ftp>" (replyMutex / replyCv / awaitingReply)
Sửa lỗi hiển thị 2 dòng ftp> cho cùng 1 lệnh: trước đây Luồng chính in prompt kế tiếp ngay sau send(), trong khi phản hồi Server lại được in ra bởi receiverLoop ở một thời điểm khác — 2 dòng chạy đua (race condition) khiến prompt xuất hiện trước khi phản hồi kịp về.
Cơ chế đồng bộ bằng condition_variable:
  • Trước khi send() lệnh đi, Luồng chính đặt cờ awaitingReply = true (bảo vệ bởi replyMutex).
  • Sau send(), Luồng chính gọi replyCv.wait(lock, [this]{ return !awaitingReply || !keepRunning; }) — chặn lại, chưa in ftp> tiếp theo.
  • receiverLoop() sau khi in xong "Server: ..." (hoặc khi mất kết nối) sẽ đặt awaitingReply = false rồi gọi replyCv.notify_one() để đánh thức Luồng chính.
  • Kết quả: prompt ftp> tiếp theo chỉ xuất hiện sau khi phản hồi của Server đã được in ra màn hình, đúng thứ tự tự nhiên của phiên làm việc.
